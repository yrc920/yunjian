# 11 · 已知限制与技术债

本文档如实记录当前实现（仓库 HEAD）的功能缺口、设计妥协与重复代码，供后续迭代参考。
每条都标注了**影响面**与**建议的改进方向**。

---

## 11.1 安全类

| # | 问题 | 影响 | 改进方向 |
| --- | --- | --- | --- |
| S1 | HTTP 网关、聊天与资源三条客户端通道均已支持 TLS（`14-tls-deployment.md`），**未配置证书时仍是明文** | 默认配置直接公网部署等于裸奔；套接字层加密不改变"密码先做可逆 XOR"的设计 | 部署时强制配证书；后续可把 XOR 换掉，改成服务端挑战-响应 |
| S2 | 服务间 gRPC 全部使用 `InsecureChannelCredentials` | 只走回环/容器内网，流量不出宿主机；跨机房部署不适用。加密的复杂度（配置、轮换要重启）大于当前收益，见 `14-tls-deployment.md` 14.11 | 拆到多机或过等保时再启用 TLS/mTLS |
| S9 | 资源下载鉴权是"同会话"粒度：请求者与文件归属人只要共处一个未解散会话即可下载，不校验该文件是否发在这个会话里 | 同事关系或同群关系就能取到对方其它会话的资源名；资源名是随机串，实际需要先知道名字才能构造请求 | 改为按 `chat_message.content` 里的资源名授权，需要同时查归档表并评估 `content LIKE` 的索引代价 |
| S10 | 本地缓存是明文 SQLite，依赖 FileVault / BitLocker | 设备遗失且磁盘未加密时，聊天记录可被直接读取 | 见 `15-local-data-security.md`：已收紧文件权限、删除清零、支持关闭缓存；合规要求"拷走也不可读"时按文档替换 SQLCipher 驱动 |
| S8 | ~~好友申请目标缺少存在性校验~~：申请入口先读目标资料，uid 不存在返回 `1011`；已是好友时按幂等成功处理。`friend_apply` 仍无数据库外键 | 删号场景下可能留下悬空申请行；当前没有删号功能 | 引入账号注销时再补外键/清理任务 |

## 11.2 可靠性类

| # | 问题 | 影响 | 改进方向 |
| --- | --- | --- | --- |
| R1 | 心跳检测粒度 30s | 客户端 10s 发一次心跳，服务端每 30s 扫一次过期会话，超时阈值 20s 加扫描延迟，半开连接约 50s 回收；期间实例负载略高于实际 | 保持 30s，或在会话表上按 uid 分片并行扫描 |
| R3 | 离线消息只能登录补拉 | 目标离线时消息已写入 `chat_message`，下次登录同步可见；没有上线推送或后台重投 | 增加离线队列/上线通知，缩短补拉延迟 |
| R4 | 已读按会话游标，不是逐条回执 | `conversation_member.last_read_message_id` 记录读到哪一条，对方把单勾改成双勾；群聊里看不到「这条有几个人读过」 | 需要逐条统计时再加 `message_read` 表，按 message_id 记录 |
| R5 | 跨实例 RPC 失败即丢弃 | 对端实例不可达时消息静默丢失 | 失败重试 + 降级为离线消息 |
| R6 | 实例探活依赖心跳 TTL | 实例崩溃后 90 秒内仍可能被分配到，新客户端会连接失败并重试 | 缩短 `inst_` TTL 到 45 秒，或由 StatusServer 主动探活 |
| R7 | 断连释放是异步尽力通知 | 状态服务不可用时释放失败，租约要等 90 秒 TTL 过期；期间重新登录会直接覆盖，不影响用户 | 本地增加释放重试队列，恢复后补发 |
| R8 | ~~用户资料缓存无 TTL~~：已统一为 1 小时 TTL，资料修改与头像上传仍会主动覆盖 | 手工改库最多 1 小时后生效 | 无 |
| R9 | MySQL 已换成 Boost.MySQL 经典协议：每次查询带 deadline（Asio 操作级取消）、会话级查询/锁超时、有界借出、坏连接剔除与健康熔断 | 数据库冻结时单条调用最多等一个 deadline（默认 5s），之后连接被丢弃重建；后续请求毫秒级失败 | 无。已验证取消后连接不复用、无泄漏 |
| R11 | 群消息落库失败统一回 `1002` 并带 `group_invalid` 标记，没有细分 `1015` | 客户端已按标记提示"你已不在该群"；服务端与日志里仍需按标记区分 | DAO 返回三态（成功/非成员/数据库错误），handler 直接映射错误码 |
| R12 | 会话列表不下发 `at_me` | 客户端靠本地记录保留"[有人@我]"，换设备或清库后标记丢失 | 服务端在列表查询里补 `EXISTS(... FIND_IN_SET(uid, mentions) ...)`，或维持客户端推导 |
| R13 | 登录在申请租约前加载好友/会话快照 | 被限流（`1105`）时这些查询白做；正常登录多花 3 次查询 | 快照与租约并行执行，失败时丢弃结果 |
| R10 | 同步好友/踢人 RPC 失败后缺少完整补偿 | 跨实例操作可能只完成一部分 | 检查每一步返回值，按 session 版本或消息 ID 做幂等补偿 |

## 11.3 性能类

| # | 问题 | 影响 | 改进方向 |
| --- | --- | --- | --- |
| P1 | GateServer 的 HTTP handler **同步阻塞**：业务处理（gRPC + MySQL）直接在 IO 线程执行 | 并发吞吐受限于 `IOContextPool` 线程数 | 把阻塞操作投递到独立线程池，或改为异步链路 |
| P2 | ChatServer 逻辑层按**会话分片为 4 个队列**，同一连接严格串行，不同连接并行 | 单个慢查询只影响落到该分片的会话；分片内仍是串行 | 吞吐再成为瓶颈时按 uid 扩容分片数 |
| P3 | 每次选路先 `SMEMBERS` 再对每个实例 `HGETALL` | O(n) 次 Redis 往返，实例数少时可接受 | 实例表在 StatusServer 内存缓存 1~2 秒，注册变更时失效 |
| P4 | 列表类查询仍逐条拼装 | 会话列表、群成员按行组装对象，没有批量聚合查询 | 数据量上来后再考虑一次查询取全字段 |
| P6 | ~~建群/邀请逐人查好友~~：已改为一条 SQL 批量校验 + 一条 INSERT 批量写入，50 人建群从 100+ 次往返降到 2 次 | 已收敛 | 无 |
| P5 | ~~用户搜索返回邮箱~~：搜索只返回公开资料（uid/name/nick/desc/sex/icon），邮箱不下发 | 已收敛 | 无 |

## 11.5 功能缺口

| # | 缺失 | 说明 |
| --- | --- | --- |
| F1 | 群聊 | 已支持建群、群聊消息、成员管理、@、公告与免打扰；被移出或解散后保留本地历史、只标记状态；未做转让群主、群头像、@所有人、逐条已读；好友列表仍无分组 |
| F2 | 媒体消息 | 图片、视频、文件已打通落库、断点上传、接收方通知与手动下载；图片与视频首帧自动补拉。视频首帧依赖 QtMultimedia 后端，缺少解码器时退化为通用图标；文件不做内容预览；表情仍为占位 |
| F3 | 客户端本地历史 | 已接入 SQLite（`users/<uid>/chat.db`）：会话、消息、好友、群与成员落库，登录按 `sync_cursor` 只拉增量，打开会话按页读库、上滑继续向前翻。首次登录会按消息号升序把历史一次回填完，之后只拉增量，因此不存在“早于已同步范围”的缺口；设置-通用 可清除本地聊天记录与已下载媒体；未做：跨会话全局搜索索引、两台设备同时补拉同一会话的冲突合并、库文件加密（当前明文 SQLite，依赖全盘加密，见 `15-local-data-security.md`） |
| F4 | 多端登录 | 租约按 uid 唯一，后登录用更高 epoch 顶掉前一个；同一账号只能一端在线，客户端收到 2007(reason=1) 后必须停止自动重连 |
| F5 | 好友删除 / 黑名单 | 单向删除（只删自己一行），双方都删除后好友关系消失，但会话与消息始终保留；重新加好友沿用同一个 `thread_id`，历史可以接上；没有黑名单 |
| F6 | 资源服务器扩展 | 只有单实例；聊天资源窗口固定 8 片，没有动态拥塞控制和超时重传；上传/下载的断点记录只存在客户端内存，退出后从第 1 片重传（服务端进度保留 1 小时）；暂停只覆盖聊天资源，头像上传仍不可暂停 |
| F7 | 原文件名冲突边界 | 视频/文件按原文件名保存，客户端按本机缓存与内容 md5 决定 `(2)` 后缀；多设备同时上传同名不同内容时仍可能冲突。另存位置只在当前进程记住，重启后“文件夹”回落到账号缓存 | 服务端在首片检查同名不同 md5 时返回冲突码，客户端换名重试；另存映射写入账号目录的小索引文件 |
| F8 | 国际化 | 客户端界面文案只有中文，`tr()` 未全面覆盖 |
| F9 | 资料变更只推给在线好友 | 昵称/签名/头像变更会实时推给在线好友（3015）。离线好友不做补偿，下次登录从 2002 回包、打开会话时从 3014 拿到最新值；没有历史推送补投 |
| F10 | 用户名不可修改 | 用户名同时是登录账号与搜索键，改名要同步 `NAME_INFO` 缓存与 `friend`/`friend_apply` 的引用，当前不提供入口 |
| F11 | 标签只是分组 | 没有"按标签群发""标签重命名"这类批量操作；改名要逐个好友改。标签也不参与权限或可见性控制 |
| F12 | 资料推送是同步分发 | 在改资料/传头像的请求路径里逐个实例发 RPC；好友数量到几百以上应改为队列异步分发 |
| F13 | 未读以服务端游标为准，没有逐条回执 | 未读由 `conversation_member.last_read_message_id` 推导，打开会话推进游标；单聊把游标通知对方显示双勾，群聊不展示逐条已读人数。多端同时在线本来会互踢，暂不需要更细的游标 |
| F14 | 时间文案不会自动跨天 | 时间条与列表时间在渲染时计算；程序挂着一整夜不重绘，第二天可能仍显示"今天"。窗口重新激活或列表重新渲染后自然恢复 |
| F15 | 重发依赖本机原文件 | 文本随时可重发；图片/视频/文件要求本机文件还在，被移动或删除后只能重新选择。重发会删掉旧失败记录再发，不会留下两条 |
| F16 | 已读状态不跨端 | 已读记在服务端，但客户端只在当前登录会话内维护状态；多端同时在线本来就会互踢，所以没有做多端已读同步 |
| F17 | 撤回不清理本地缓存 | 撤回后界面不再显示正文与附件，但已经下载到本机的图片/文件仍留在缓存目录，没有随之删除 |
| F18 | 删好友对端无感知 | 单向删除只改自己那行，不推送；对方要等下次登录才会发现列表变化，期间他仍能打开旧会话，只是发消息会失败 |
| F19 | 删除后重新加回需要重新申请 | 删除会清掉自己发出的申请记录；任何一方都可以重新发申请，对方同意后两行关系重新建立。没有"撤销删除"的快捷入口 |

## 11.6 改进优先级建议

按"风险 × 成本"排序，建议的推进顺序：

1. **S2**（安全，成本中）：服务间 gRPC 的 TLS/mTLS。好友申请目标校验已完成。
   客户端三条通道的 TLS 已完成（`14-tls-deployment.md`），部署时配证书即可生效。
2. **R2**（可靠性，成本中）：断线重连与 token 复用；必须识别 2007 的 reason，
   异地登录时停止自动重连，否则会和新会话互踢。
3. **C1 / C9**（结构，成本低）：继续收敛 DAO 与 QML 中的重复结构；错误码与 `UserCache` 已完成收敛。
4. **R4**（功能，成本中高）：已读回执与离线重投；本地历史缓存已完成，余下是库内搜索。
5. **P1 / P2**（性能，成本高）：GateServer 同步阻塞与 ChatServer 单逻辑线程，建议在吞吐成为瓶颈后再做。

> 会话控制面（租约、epoch、实例注册、路由缓存）与三条低成本安全项（登出吊销、
> 验证码一次性、发送限流）已完成。若要用于生产环境，至少需完成第 1 组与第 2 组。
