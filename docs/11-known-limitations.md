# 11 · 已知限制与技术债

本文档如实记录当前实现（仓库 HEAD）的功能缺口、设计妥协与重复代码，供后续迭代参考。
每条都标注了**影响面**与**建议的改进方向**。

---

## 11.1 安全类

| # | 问题 | 影响 | 改进方向 |
| --- | --- | --- | --- |
| S1 | 密码在 HTTP 链路上仅经客户端 `xorString()` 做**可逆 XOR 变形**（按长度取模，只处理前 `len % 255` 个字符），网关未启用 TLS | 任何中间人可还原明文密码 | 网关启用 HTTPS（Beast 支持 `ssl_stream`）；客户端改为在 TLS 之上传输，或至少改用不可逆的服务端挑战-响应 |
| S2 | 服务间 gRPC 全部使用 `InsecureChannelCredentials` | 内网可信前提下的设计，跨机房部署不适用 | 启用 TLS 或 mTLS |
| S3 | Token（UUID）**无有效期、无刷新、无吊销**；`utoken_<uid>` 永不过期 | token 泄露即长期有效 | `SETEX` + 刷新机制；登出时主动删除 |
| S5 | 验证码无发送频率限制 | 同一邮箱可被滥用于邮件轰炸 | 按邮箱 + IP 做限流（Redis 计数器 + TTL） |
| S6 | 注册/改密成功后未删除 `code_<email>` | 10 分钟内验证码可重复使用 | 成功后 `DEL` |
| S8 | 好友申请目标缺少存在性/外键校验；发消息已在 DAO 校验好友关系或会话成员 | 好友申请可指向不存在的 uid；消息发送已不能绕过好友关系 | 补目标存在性校验与 `friend_apply` 的外键/唯一约束 |

## 11.2 可靠性类

| # | 问题 | 影响 | 改进方向 |
| --- | --- | --- | --- |
| R1 | 心跳检测粒度 60s | 客户端 10s 发一次心跳，服务端每 60s 才扫一次过期会话，超时阈值 20s 加上扫描延迟，半开连接接近 80s 才回收，期间 `logincount` 偏高 | 扫描间隔降到心跳间隔的 2~3 倍 |
| R2 | 客户端无断线重连 | 网络抖动后只提示「已离线」并回到登录页，需重新输入密码 | `TcpMgr` 增加重连退避与自动重新登录（复用 token） |
| R3 | 离线消息只能登录补拉 | 目标离线时消息已写入 `chat_message`，下次登录同步可见；没有上线推送或后台重投 | 增加离线队列/上线通知，缩短补拉延迟 |
| R4 | 无已读回执 | 1018 回执驱动“发送中 / 已发送 / 失败”；“未读 / 已读”目前只是 UI 占位，`chat_message.status` 没有读取/更新闭环 | 增加 `message_read` 表与已读上报，持久化 status |
| R5 | 跨实例 RPC 失败即丢弃 | 对端实例不可达时消息静默丢失 | 失败重试 + 降级为离线消息 |
| R6 | 无服务探活 | StatusServer 无法感知实例已崩溃，仍可能分配 | 心跳上报 + 过期剔除（`logincount` 加时间戳） |
| R7 | 断连清理依赖 Redis 锁与连接可用性；失败后缺少补偿 | `uip_` / `usession_` 可能残留 | 给在线状态加 TTL，并按 session 标识进行原子续期与删除 |
| R8 | 用户资料缓存无 TTL，只靠写入方主动覆盖：头像上传（ResourceServer）与本人改资料（ChatServer）会刷新 `ubaseinfo_` / `nameinfo_`，其余路径（手工改库、其他服务写入）不会自动失效 | 非这两条路径改动的资料可能长期读到旧值 | 统一收敛为「写库后删键」，或给缓存加 TTL |
| R9 | Redis/MySQL 连接池缺少完整的连接超时、失效剔除和重连策略 | 初始化无可用连接或运行中断网时，调用可能长时间阻塞；gRPC deadline 不能代替数据库超时 | 增加有界等待、健康检测与重连退避 |
| R10 | 同步好友/踢人 RPC 失败后缺少完整补偿 | 跨实例操作可能只完成一部分 | 检查每一步返回值，按 session 版本或消息 ID 做幂等补偿 |

## 11.3 性能类

| # | 问题 | 影响 | 改进方向 |
| --- | --- | --- | --- |
| P1 | GateServer 的 HTTP handler **同步阻塞**：业务处理（gRPC + MySQL）直接在 IO 线程执行 | 并发吞吐受限于 `IOContextPool` 线程数 | 把阻塞操作投递到独立线程池，或改为异步链路 |
| P2 | ChatServer 逻辑层**单线程串行** | 单实例消息处理吞吐有上限；慢查询会阻塞整个队列 | 按 uid 分片多队列 + 多消费者（`UserMgr` 已有互斥锁，仍需保证跨操作一致性） |
| P3 | 每次选路对**每个实例**发起一次 `HGET` | O(n) 次 Redis 往返 | 一次 `HGETALL logincount` 后在内存比较 |
| P4 | MySQL 访问未体现批量/预编译复用 | 单次请求开销偏大 | 视需要引入批量查询与语句缓存 |
| P5 | 用户搜索返回邮箱等完整资料 | 无用字段传输与缓存 | 拆分"搜索结果"与"完整资料"两套结构 |

## 11.4 代码结构类

| # | 问题 | 位置 | 改进方向 |
| --- | --- | --- | --- |
| C1 | `GetBaseInfo` 逻辑在 **三处重复** | `LogicSystem`、`ChatServiceImpl`、`ChatGrpcClient`（ChatServer） | 收敛到 `UserMgr` 或独立的 `UserCache` 组件 |
| C2 | `ErrorCodes` 枚举在 GateServer / StatusServer / ChatServer **各自复制一份**（1001–1009，ChatServer 多 1010/1011） | 三处 `include/const.h` | 抽到公共头，避免漏改导致语义漂移 |
| C3 | `IOContextPool` / `ConfigMgr` / `RedisMgr` / `MysqlMgr` / `MysqlDao` / `Singleton` 在五个服务中**逐份复制** | `services/*/` | 抽取为公共静态库，各服务链接；代价是服务间的独立性下降，需权衡 |
| C4 | `StatusServer::ChatGrpcClient` 为**死代码**，且构造用的是 TCP 端口而非 RPC 端口 | `services/StatusServer/` | 删除，或修正端口语义后在需要时启用 |
| C5 | `ChatServer::StatusGrpcClient` 已链接但**未被调用**；`StatusService::Login` 与 ChatServer 自行读 Redis 校验 token 逻辑重复 | `services/ChatServer/`、`services/StatusServer/` | 统一为"ChatServer 调 StatusServer::Login"，收敛校验入口 |
| C6 | proto 中 `RplyAddFriend`、`SendChatMsg` 已定义但无实现/无调用 | `proto/message.proto` | 实现或删除 |
| C7 | `IPCOUNTPREFIX`（`ipcount_`）等常量已无引用 | `ChatServer/include/const.h` | 清理 |
| C8 | `LogicSystem` handler 返回值 `bool` 未被使用 | GateServer | 接口简化或真正使用返回值表达"是否成功" |

## 11.5 功能缺口

| # | 缺失 | 说明 |
| --- | --- | --- |
| F1 | 群聊 | 已支持建群、群聊消息、成员管理、@、公告与免打扰；未做转让群主、群头像、@所有人、逐条已读；好友列表仍无分组 |
| F2 | 媒体消息 | 图片、视频、文件已打通落库、断点上传、接收方通知与手动下载；图片与视频首帧自动补拉。视频首帧依赖 QtMultimedia 后端，缺少解码器时退化为通用图标；文件不做内容预览；表情仍为占位 |
| F3 | 客户端本地消息缓存 | 服务端 `chat_message` 已持久化；客户端仍只存内存，重启或换设备后需从服务端全量拉取；后续接入 SQLite 与本地增量游标 |
| F4 | 多端登录 | `uip_<uid>` 只保留最后一个登录位置；多端会互相踢掉（后登录覆盖） |
| F5 | 好友删除 / 黑名单 | 只有添加与同意 |
| F6 | 资源服务器扩展 | 只有单实例；聊天资源窗口固定 8 片，没有动态拥塞控制和超时重传；上传/下载的断点记录只存在客户端内存，退出后从第 1 片重传（服务端进度保留 1 小时）；暂停只覆盖聊天资源，头像上传仍不可暂停 |
| F7 | 原文件名冲突边界 | 视频/文件按原文件名保存，客户端按本机缓存与内容 md5 决定 `(2)` 后缀；多设备同时上传同名不同内容时仍可能冲突。另存位置只在当前进程记住，重启后“文件夹”回落到账号缓存 | 服务端在首片检查同名不同 md5 时返回冲突码，客户端换名重试；另存映射写入账号目录的小索引文件 |
| F8 | 国际化 | 客户端界面文案只有中文，`tr()` 未全面覆盖 |
| F9 | 资料变更只推给在线好友 | 昵称/签名/头像变更会实时推给在线好友（1051）。离线好友不做补偿，下次登录从 1006 回包、打开会话时从 1050 拿到最新值；没有历史推送补投 |
| F10 | 用户名不可修改 | 用户名同时是登录账号与搜索键，改名要同步 `NAME_INFO` 缓存与 `friend`/`friend_apply` 的引用，当前不提供入口 |
| F11 | 标签只是分组 | 没有"按标签群发""标签重命名"这类批量操作；改名要逐个好友改。标签也不参与权限或可见性控制 |
| F12 | 资料推送是同步分发 | 在改资料/传头像的请求路径里逐个实例发 RPC；好友数量到几百以上应改为队列异步分发 |
| F13 | 未读以服务端为准，但没有"已读回执"级别的游标 | 未读来自 `is_read`，登录时恢复；打开会话即整段标已读，不记录"读到第几条"的中间状态。多端同时在线本来会互踢，暂不需要更细的游标 |
| F14 | 时间文案不会自动跨天 | 时间条与列表时间在渲染时计算；程序挂着一整夜不重绘，第二天可能仍显示"今天"。窗口重新激活或列表重新渲染后自然恢复 |
| F15 | 重发依赖本机原文件 | 文本随时可重发；图片/视频/文件要求本机文件还在，被移动或删除后只能重新选择。重发会删掉旧失败记录再发，不会留下两条 |
| F16 | 已读状态不跨端 | 已读记在服务端，但客户端只在当前登录会话内维护状态；多端同时在线本来就会互踢，所以没有做多端已读同步 |
| F17 | 撤回不清理本地缓存 | 撤回后界面不再显示正文与附件，但已经下载到本机的图片/文件仍留在缓存目录，没有随之删除 |
| F18 | 删好友对端无感知 | 单向删除只改自己那行，不推送；对方要等下次登录才会发现列表变化，期间他仍能打开旧会话，只是发消息会失败 |
| F19 | 删除后重新加回需要重新申请 | 删除会清掉自己发出的申请记录；任何一方都可以重新发申请，对方同意后两行关系重新建立。没有"撤销删除"的快捷入口 |

## 11.6 改进优先级建议

按"风险 × 成本"排序，建议的推进顺序：

1. **S1 / S3 / S6**（安全，成本低）：HTTP 上 TLS、token 加 TTL 与登出删除、验证码用后即删。
2. **R2**（可靠性，成本中）：断线重连与 token 复用，直接决定用户体验。
3. **C1 / C2 / C4 / C5**（结构，成本低）：消除重复实现与死代码，降低后续改动出错概率。
4. **R4 / F3**（功能，成本中高）：客户端本地消息缓存、已读回执与离线重投。
5. **P1 / P2**（性能，成本高）：异步化与多队列，建议在单机吞吐成为实际瓶颈后再做。

> 本项目的定位是学习与工程实践，上述缺口多数是"有意留白"而非缺陷；
> 若要用于生产环境，至少需完成第 1 组（S1/S3/S6）与第 2 组（R1/R2）。
